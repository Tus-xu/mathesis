# Research Workspace VNext

# 科研智能工作台产品定义、前后端能力与质量冻结总提示词

```text
你现在负责实现一个真正可以提供给科研工作者长期使用的：

Research Workspace / 科研智能工作台

你收到的两张界面图：

1. 科研工作台：有限元误差分析
2. 科研工作台：有限元论文写作界面

均为 1672 × 941。

它们不是“灵感图”。

它们是本产品的：

GOLDEN PRODUCT REFERENCE
GOLDEN INFORMATION ARCHITECTURE
GOLDEN VISUAL REFERENCE

它们已经确定了科研端最终产品的主要形态。

你的任务不是重新设计一个你认为更现代的科研平台。

你的任务是：

让真实产品在视觉、交互、业务逻辑、数据流、
AI 能力、文献能力、LaTeX 能力和可靠性上，
完整实现这两张图所表达的产品。

==================================================
0. 本文档的性质
==================================================

本文档定义的是：

产品必须是什么。

而不是：

代码必须怎么写。

具体：

采用什么框架、
哪些现有模块继续复用、
哪些模块需要适配、
哪些接口需要重构、
数据库如何映射、
服务如何拆分、

由你根据现有科研端真实代码自行判断。

但是最终产品行为不得偏离本文档。

特别注意：

本文档出现的：

ResearchProject
ResearchContext
Citation Engine
Compile capability
Agent Runtime
Evidence capability

等名称首先代表“领域能力”。

它们并不意味着：

必须创建同名的新服务、
新数据库表、
新目录、
新 V2 系统。

如果现有科研端已经存在对应能力，
应该让现有能力满足这里定义的产品契约。

==================================================
1. 产品定位
==================================================

科研端不是：

科研 ERP；
复杂项目管理系统；
表单式 AI 工具集合；
模型调用控制台；
实验室管理软件；
聊天机器人套壳；
简单 PDF 阅读器；
简单 Overleaf 克隆。

科研端的定位是：

AI-native Research Workspace。

面向：

阅读论文、
理解论文、
进行理论推导、
管理科研证据、
形成科研笔记、
编写论文、
修改论文、
管理引用、
检查公式、
解决 LaTeX 问题

的科研人员。

它应该让用户产生这种感觉：

“我的论文、文献、笔记和写作全部存在一个项目中，
AI 了解我当前正在看什么、写什么、研究什么，
并且能够基于真实证据帮助我完成科研工作。”

而不是：

“这里有十几个 AI 小工具，
我要自己选择功能、输入参数、复制结果。”

==================================================
2. 产品最高级核心模型：Research Project
==================================================

整个科研工作台必须围绕：

Research Project

组织。

例如：

有限元误差分析

就是一个 Research Project。

一个项目下可以拥有：

论文 / 文献
草稿
LaTeX 文件
BibTeX
图片附件
笔记
引用记录
Research Session
AI 对话
证据
历史修改
编译结果

用户不是：

“进入 PDF 工具”

然后：

“再进入写作工具”。

而是始终处于：

有限元误差分析

这个 Project 内。

READ / WRITE

只是同一科研项目的两种 Workspace。

涉及：

学术判断

证据。

==================================================
34. 推导校验
==================================================

36. 引用补全
==================================================

然后寻找：

作者
年份
对应结论

==================================================
37. Citation 不允许伪造
==================================================

不能让 LLM 自己生成：

不存在的 DOI
不存在的论文
错误作者

未验证引用。

不能伪装成真实来源。

==================================================

然后：

插入：

\cite{...}
```

这版和前面最大的区别是：**它不再告诉智能体“先创建什么服务、然后改什么目录”**，而是定义了一份完整的“产品宪法”。这样你的 coding agent 可以自己研究已有科研端：原来已经有 PDF、LaTeX、RAG、模型网关、数学验证，它完全可以复用；缺什么再补什么。**但无论底层怎么改，最后 READ、WRITE、Research Agent、Evidence、Citation、LaTeX、Project Context 的用户体验和真实能力都不能乱。**

另外我建议你实际交给智能体时，**这份不要和超长施工 Prompt 混成一个文件**。OpenAI 对大型 agent-first 工程的经验恰恰说明，超大的单体说明会挤占上下文并产生规则漂移；更好的做法是让这一份成为类似 `RESEARCH_PRODUCT_CONTRACT.md` 的最高产品规范，AGENTS/总提示词只明确一句“科研端产品行为与视觉必须遵循此 Contract”，这样后面不管是哪个智能体改前端、后端还是 Agent，它都有唯一产品真相源。([OpenAI][3])
